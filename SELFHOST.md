

## Внедрение Renovate OSS для автоматизации обновления зависимостей

###  1. Контекст

В проекте используются:
  - внутренний npm-реестр на базе Nexus
  - CI/CD инфраструктура
  - semantic-release для публикации пакетов

Необходимо внедрить автоматическое обновление зависимостей (включая внутренние пакеты) с минимальной инфраструктурной сложностью и без нарушения требований безопасности.

Рассматривались варианты использования: 
  1. Renovate SaaS (GitLub App / Bot)
  2. Renovate OSS (self-hosted)
  3. Развертывание отдельного сервиса
  4. Запуск через CI/CD runner


### 2. Требования

Функциональные
  - Автоматическое создание PR для обновления зависимостей
  - Поддержка внутреннего Nexus
  - Работа с semantic-release
  - Поддержка правил (automerge, major/minor, stability-days)

Нефункциональные 
  - Минимальная инфраструктурная нагрузка
  - Отсутствие постоянно работающих сервисов
  - Соответствие security-политикам (токены внутри периметра)
  - Простота масштабирования



### 3. Рассмотренные альтернативы

#### 3.1 Renovate SaaS (GitLub App)

Описание: Использование облачного Renovate Bot.

Преимущества:
  - Простота подключения
  - Нет необходимости управлять инфраструктурой

Недостатки:
  - Необходимость передачи доступа к Nexus во внешний сервис
  - Возможные ограничения сетевого доступа
  - Ограниченный контроль логирования
  - Нарушение внутреннего security-контура

Вывод: Не рекомендуется при использовании приватного Nexus.


#### 3.2 Отдельный self-hosted сервис (постоянно работающий)

Описание: Развертывание Renovate как постоянно работающего сервиса (Docker, Kubernetes).

Преимущества: 
  - Централизованное управление
  - Подходит для большого числа репозиториев

Недостатки: 
  - Избыточность
  - Увеличение операционной сложности
  - Требует поддержки инфраструктуры
  - Не даёт функциональных преимуществ для текущего масштаба

Вывод: Overengineering для текущей задачи.


#### 3.3 Renovate OSS через CI/CD runner (CLI или Docker)

Описание: Запуск Renovate OSS как CI job по расписанию.

Вариант A — Docker-образ 
  - Используется образ renovate/renovate
  - Контейнер запускается в CI
  - После выполнения уничтожается

Вариант B — CLI (Node.js) 
  - Используется npx renovate
  - Запуск в среде runner с Node.js
  - Процесс завершается после выполнения

Преимущества:
  - Полный функционал Renovate
  - Stateless-архитектура
  - Нет постоянно работающих сервисов
  - Токены остаются внутри инфраструктуры
  - Полный контроль логов
  - Соответствие best practice

Недостатки:
  - Запуск не realtime (по расписанию)
  - Требуется настройка cron

Вывод: Соответствует требованиям проекта.


### 4. Архитектурное решение

Принято решение использовать:

Renovate OSS, запускаемый как CI/CD job по расписанию, предпочтительно через Docker-образ.

CLI-вариант допускается как технически возможный, но Docker-вариант предпочтителен из-за:
  - изоляции среды
  - предсказуемости runtime
  - независимости от версии Node
  - удобства поддержки DevOps


### 5. Архитектура процесса

Процесс выполнения:
  1. CI запускается по расписанию.
  2. Поднимается контейнер (или запускается CLI).
  3. Renovate:
      - анализирует зависимости
      - проверяет версии в Nexus
      - создаёт PR через GitHub API
  4. Job завершается.
  5. Среда выполнения уничтожается.
  6. Состояние сохраняется исключительно в GitHub.


### 6. Интеграция с semantic-release

Связка процессов:
  1. Renovate создаёт PR.
  2. PR проходит review и merge.
  3. CI запускает semantic-release.
  4. Публикуется новая версия пакета.

Renovate не требует дополнительного сервиса для интеграции.


### 7. Что не требуется

Для текущего масштаба не требуется:
  - Renovate SaaS
  - Постоянно работающий сервер
  - Kubernetes
  - Nginx
  - Веб-интерфейс или control-plane

Renovate является stateless CLI-инструментом.


### 8. Последствия решения

Положительные
  - Простая архитектура
  - Минимальная операционная нагрузка
  - Соответствие security-политикам
  - Масштабируемость
  - Прозрачность логирования

Ограничения
  - Запуск по расписанию (не event-driven)
  - Требуется контроль CI-конфигурации


## 9. Итог

Для репозиториев оптимальным и достаточным решением является:

Запуск Renovate OSS как CI/CD job по расписанию с использованием Docker-образа.

Это обеспечивает необходимую функциональность без избыточной инфраструктуры и соответствует требованиям безопасности.
